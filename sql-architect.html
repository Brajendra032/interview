Multi-Tenant Database Schema Design

Architecture Design Senior

Problem: Design a database schema for a multi-tenant SaaS application where multiple companies share the same infrastructure but their data must be completely isolated.

Key Considerations:
  • Data Isolation: Each tenant's data must be completely separate and secure
  • Scalability: System must handle thousands of tenants efficiently
  • Performance: Queries should be fast even with millions of records
  • Resource Optimization: Minimize database overhead per tenant
  • Maintenance: Easy to add/remove tenants without affecting others
📋 Complete Solution: Multi-Tenant Schema
-- ============================================ -- MULTI-TENANT SAAS DATABASE SCHEMA -- ============================================ -- Step 1: Tenant Management Table -- This table stores information about each tenant (company) CREATE TABLE tenants ( id BIGINT PRIMARY KEY AUTO_INCREMENT, name VARCHAR(255) NOT NULL, subdomain VARCHAR(100) UNIQUE NOT NULL, database_name VARCHAR(100) UNIQUE NOT NULL, status ENUM('active', 'suspended', 'deleted') DEFAULT 'active', created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP, INDEX idx_subdomain (subdomain), INDEX idx_status (status) ); -- Step 2: User Management (Central) -- All users belong to a tenant CREATE TABLE users ( id BIGINT PRIMARY KEY AUTO_INCREMENT, tenant_id BIGINT NOT NULL, email VARCHAR(255) NOT NULL, password_hash VARCHAR(255) NOT NULL, role ENUM('admin', 'user', 'moderator') DEFAULT 'user', status ENUM('active', 'inactive', 'banned') DEFAULT 'active', created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP, UNIQUE KEY unique_tenant_email (tenant_id, email), INDEX idx_tenant_status (tenant_id, status), FOREIGN KEY (tenant_id) REFERENCES tenants(id) ON DELETE CASCADE ); -- Step 3: Per-tenant tables (example: Posts) -- This table includes tenant_id for data isolation CREATE TABLE posts ( id BIGINT PRIMARY KEY AUTO_INCREMENT, tenant_id BIGINT NOT NULL, -- Critical: Every row has tenant_id user_id BIGINT NOT NULL, title VARCHAR(500) NOT NULL, content TEXT, status ENUM('draft', 'published', 'archived') DEFAULT 'draft', published_at TIMESTAMP NULL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP, -- Indexes for performance INDEX idx_tenant_status (tenant_id, status), INDEX idx_user_created (user_id, created_at), INDEX idx_published (published_at), -- Fulltext search index FULLTEXT idx_title_content (title, content), -- Foreign keys for data integrity FOREIGN KEY (tenant_id) REFERENCES tenants(id), FOREIGN KEY (user_id) REFERENCES users(id) ) PARTITION BY HASH(tenant_id) PARTITIONS 64; -- Step 4: Optimized Stored Procedure -- This ensures tenant isolation at the database level DELIMITER // CREATE PROCEDURE get_tenant_posts(IN tenantId BIGINT, IN limitCount INT) BEGIN SELECT p.*, u.email as author_email FROM posts p JOIN users u ON p.user_id = u.id WHERE p.tenant_id = tenantId -- Always filter by tenant_id AND p.status = 'published' ORDER BY p.published_at DESC LIMIT limitCount; END // DELIMITER ; -- Step 5: Tenant-specific indexes for better performance CREATE INDEX idx_tenant_posts_recent ON posts (tenant_id, published_at DESC, status); CREATE INDEX idx_tenant_user_posts ON posts (tenant_id, user_id, created_at DESC);
🧠 How It Works:
1. Tenant Isolation: Every table includes tenant_id. All queries MUST filter by tenant_id first.
2. Partitioning: Tables are partitioned by tenant_id for faster queries and easier maintenance.
3. Security: Stored procedures enforce tenant isolation at database level.
4. Performance: Composite indexes on (tenant_id, other_columns) make queries fast.
💡 Real-World Example Query
-- Get all published posts for tenant ID 5 -- This query is automatically isolated to tenant 5 CALL get_tenant_posts(5, 20); -- Or using direct query (always include tenant_id in WHERE) SELECT p.*, u.email FROM posts p JOIN users u ON p.user_id = u.id WHERE p.tenant_id = 5 -- CRITICAL: Always filter by tenant_id AND p.status = 'published' ORDER BY p.published_at DESC LIMIT 20;

Advanced Indexing Strategies

Performance Optimization Senior

Problem: How do you design and implement advanced indexing strategies for high-performance database queries?

Indexing Best Practices:
  • Index Foreign Keys: Automatically index all foreign key columns
  • Composite Indexes: Use for multi-column WHERE clauses
  • Covering Indexes: Include all query columns in index for maximum speed
  • Monitor Usage: Regularly check and remove unused indexes
  • Partial Indexes: Index only specific rows to save space
📋 Complete Indexing Strategies
-- ============================================ -- ADVANCED INDEXING STRATEGIES -- ============================================ -- 1. COMPOSITE INDEX for Common Query Patterns -- Query Pattern: SELECT * FROM orders WHERE customer_id = ? AND order_date >= ? AND status = 'active' CREATE INDEX idx_orders_customer_date_status ON orders (customer_id, order_date DESC, status) WHERE status = 'active'; -- Example Usage: SELECT * FROM orders WHERE customer_id = 123 AND order_date >= '2024-01-01' AND status = 'active'; -- This query uses the composite index efficiently -- 2. COVERING INDEX (includes all columns needed by query) -- Query: SELECT customer_id, order_date, total FROM orders WHERE status = 'shipped' -- Covering index means query reads ONLY from index, not table (10x faster!) CREATE INDEX idx_orders_covering ON orders (status, customer_id, order_date, total) WHERE status = 'shipped'; -- Example Usage: SELECT customer_id, order_date, total FROM orders WHERE status = 'shipped'; -- Database reads only from index, never touches table! -- 3. PARTIAL INDEX for specific conditions -- Only index active users to reduce index size CREATE INDEX idx_active_users_email ON users (email) WHERE status = 'active' AND deleted_at IS NULL; -- Example Usage: SELECT * FROM users WHERE email = 'john@example.com' AND status = 'active' AND deleted_at IS NULL; -- Index is smaller and faster because it only contains active users -- 4. FUNCTIONAL INDEX for computed values -- Index on email domain for segmentation queries CREATE INDEX idx_users_email_domain ON users (SUBSTRING_INDEX(email, '@', -1)); -- Example Usage: SELECT * FROM users WHERE SUBSTRING_INDEX(email, '@', -1) = 'gmail.com'; -- This query uses the functional index -- 5. SPATIAL INDEX for location-based queries -- For geo-location features (Uber, food delivery apps) CREATE TABLE locations ( id BIGINT PRIMARY KEY, name VARCHAR(255), coordinates POINT NOT NULL, SPATIAL INDEX idx_coordinates (coordinates) ); -- Example: Find nearby locations (within 1km) SELECT name, ST_Distance(coordinates, ST_PointFromText('POINT(40.7128 -74.0060)')) as distance FROM locations WHERE ST_Contains( ST_Buffer(ST_PointFromText('POINT(40.7128 -74.0060)'), 1000), coordinates ) ORDER BY distance; -- Returns all locations within 1km of New York City coordinates -- 6. INDEX MAINTENANCE and MONITORING -- Check which indexes are being used SELECT object_schema, object_name, index_name, count_read, count_write, count_fetch FROM performance_schema.table_io_waits_summary_by_index_usage WHERE object_schema NOT IN ('mysql', 'sys', 'performance_schema') ORDER BY (count_read + count_write) DESC; -- Find UNUSED indexes (candidates for removal) SELECT object_schema, object_name, index_name, count_read, count_write FROM performance_schema.table_io_waits_summary_by_index_usage WHERE count_read = 0 AND count_write = 0 AND object_schema NOT IN ('mysql', 'sys', 'performance_schema'); -- These indexes are wasting space and slowing down writes!
🎯 Key Takeaways:
Covering Index: If index contains all columns in SELECT, query is 10x faster (no table access).
Composite Index Order: Index columns in order of selectivity (most selective first).
Partial Index: Reduces index size by only indexing relevant rows.
Monitor Regularly: Unused indexes slow down INSERT/UPDATE operations.

Database Partitioning & Sharding

Scalability Architecture Senior

Problem: Implement database partitioning and sharding strategies for handling massive datasets and high concurrency.

Partitioning vs Sharding:
  • Partitioning: Divide table into smaller pieces within the same database (faster queries, easier maintenance)
  • Sharding: Distribute data across multiple database instances (horizontal scaling, requires application logic)
  • Hybrid: Combine both for optimal performance at massive scale
📋 Complete Partitioning Examples
-- ============================================ -- DATABASE PARTITIONING STRATEGIES -- ============================================ -- 1. RANGE PARTITIONING (by date) - Most Common -- Perfect for time-series data (logs, events, transactions) CREATE TABLE user_activity ( id BIGINT PRIMARY KEY AUTO_INCREMENT, user_id BIGINT NOT NULL, activity_type VARCHAR(50) NOT NULL, activity_data JSON, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, INDEX idx_user_created (user_id, created_at) ) PARTITION BY RANGE (YEAR(created_at)) ( PARTITION p2020 VALUES LESS THAN (2021), PARTITION p2021 VALUES LESS THAN (2022), PARTITION p2022 VALUES LESS THAN (2023), PARTITION p2023 VALUES LESS THAN (2024), PARTITION p_future VALUES LESS THAN MAXVALUE ); -- Add new partition for next year (maintenance task) ALTER TABLE user_activity ADD PARTITION ( PARTITION p2024 VALUES LESS THAN (2025) ); -- Query only scans relevant partition (much faster!) SELECT * FROM user_activity WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'; -- Only scans p2024 partition, ignores all other years! -- 2. HASH PARTITIONING (for even distribution) -- Distributes data evenly across partitions CREATE TABLE sessions ( id BIGINT PRIMARY KEY AUTO_INCREMENT, user_id BIGINT NOT NULL, session_token VARCHAR(255) UNIQUE NOT NULL, expires_at TIMESTAMP NOT NULL, data JSON, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, INDEX idx_token (session_token), INDEX idx_expires (expires_at) ) PARTITION BY HASH(id) PARTITIONS 64; -- Data distributed evenly across 64 partitions -- 3. LIST PARTITIONING (by category) -- Partition by specific values (regions, types, etc.) CREATE TABLE notifications ( id BIGINT PRIMARY KEY AUTO_INCREMENT, user_id BIGINT NOT NULL, type ENUM('email', 'sms', 'push', 'in_app') NOT NULL, title VARCHAR(255) NOT NULL, message TEXT, read_at TIMESTAMP NULL, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, INDEX idx_user_read (user_id, read_at) ) PARTITION BY LIST (type) ( PARTITION p_email VALUES IN ('email'), PARTITION p_sms VALUES IN ('sms'), PARTITION p_push VALUES IN ('push'), PARTITION p_inapp VALUES IN ('in_app') ); -- Query specific notification type (only scans one partition) SELECT * FROM notifications WHERE type = 'email' AND created_at >= '2024-01-01'; -- Only scans p_email partition! -- 4. SUBPARTITIONING (Range + Hash) - Advanced -- Combines two partitioning strategies CREATE TABLE orders ( id BIGINT PRIMARY KEY AUTO_INCREMENT, customer_id BIGINT NOT NULL, order_date DATE NOT NULL, total DECIMAL(10,2) NOT NULL, status ENUM('pending', 'processing', 'shipped', 'delivered') DEFAULT 'pending', created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, INDEX idx_customer_date (customer_id, order_date) ) PARTITION BY RANGE (YEAR(order_date)) SUBPARTITION BY HASH(customer_id) SUBPARTITIONS 4 ( PARTITION p2023 VALUES LESS THAN (2024) ( SUBPARTITION p2023_h0, SUBPARTITION p2023_h1, SUBPARTITION p2023_h2, SUBPARTITION p2023_h3 ), PARTITION p2024 VALUES LESS THAN (2025) ( SUBPARTITION p2024_h0, SUBPARTITION p2024_h1, SUBPARTITION p2024_h2, SUBPARTITION p2024_h3 ) ); -- First partitioned by year, then by customer_id hash -- Total: 8 subpartitions (2 years × 4 hash partitions)
💡 When to Use Each Type:
Range Partitioning: Time-series data, logs, events (drop old partitions easily).
Hash Partitioning: Even distribution, no natural partition key.
List Partitioning: Known categories, regions, types.
Subpartitioning: Very large tables needing both time and distribution partitioning.

Query Optimization & Performance Tuning

Performance Optimization Senior

Problem: How do you analyze and optimize slow database queries for enterprise applications?

Optimization Workflow:
  • Step 1: Enable slow query log and analyze patterns
  • Step 2: Use EXPLAIN to understand query execution plans
  • Step 3: Identify bottlenecks (missing indexes, table scans, N+1 queries)
  • Step 4: Implement appropriate optimizations
  • Step 5: Monitor performance improvements
📋 Query Optimization Techniques
-- ============================================ -- QUERY OPTIMIZATION TECHNIQUES -- ============================================ -- 1. ANALYZE QUERY PERFORMANCE -- Always use EXPLAIN to see execution plan EXPLAIN FORMAT=JSON SELECT u.name, COUNT(o.id) as order_count, SUM(o.total) as total_spent FROM users u LEFT JOIN orders o ON u.id = o.customer_id WHERE u.created_at >= '2023-01-01' AND u.status = 'active' GROUP BY u.id HAVING total_spent > 1000 ORDER BY total_spent DESC LIMIT 50; -- Look for: type (ALL = bad, index = good), rows scanned, key used
❌ SLOW: Correlated Subquery
-- This runs subquery for EACH user row! SELECT u.name, (SELECT COUNT(*) FROM orders o WHERE o.customer_id = u.id) as order_count FROM users u; -- If you have 10,000 users, this runs 10,000 subqueries!
✅ FAST: JOIN with Aggregation
-- This runs ONE query for all users SELECT u.name, COUNT(o.id) as order_count FROM users u LEFT JOIN orders o ON u.id = o.customer_id GROUP BY u.id; -- Single query, much faster!
❌ SLOW: OFFSET for Deep Pages
-- OFFSET scans all previous rows SELECT * FROM products ORDER BY created_at DESC LIMIT 50 OFFSET 999950; -- Database must scan 999,950 rows before returning results!
✅ FAST: Seek Method
-- Uses index to jump directly to position SELECT * FROM products WHERE (created_at, id) < ('2024-01-01', 1000000) ORDER BY created_at DESC, id DESC LIMIT 50; -- Jumps directly to position using index!
-- 3. OPTIMIZE COMPLEX WHERE CONDITIONS -- Create composite index matching query pattern CREATE INDEX idx_users_complex ON users (status, created_at, last_login_at) WHERE status IN ('active', 'premium'); -- Query uses this index efficiently SELECT * FROM users WHERE status = 'active' AND created_at >= '2024-01-01' AND last_login_at >= '2024-01-01'; -- 4. OPTIMIZE FULL-TEXT SEARCH -- ❌ SLOW: Using LIKE (scans entire table) SELECT * FROM articles WHERE title LIKE '%database optimization%' OR content LIKE '%database optimization%'; -- Scans every row, very slow on large tables -- ✅ FAST: Using MATCH AGAINST (uses fulltext index) SELECT * FROM articles WHERE MATCH(title, content) AGAINST('database optimization' IN NATURAL LANGUAGE MODE) ORDER BY MATCH(title, content) AGAINST('database optimization' IN NATURAL LANGUAGE MODE) DESC; -- Uses fulltext index, 100x faster! -- 5. AVOID SELECT * (only select needed columns) -- ❌ SLOW: Selects all columns SELECT * FROM users WHERE id = 123; -- ✅ FAST: Select only needed columns SELECT id, name, email FROM users WHERE id = 123; -- Less data transfer, faster query
🎯 Optimization Rules:
1. Always EXPLAIN first - Understand what the database is doing
2. Replace correlated subqueries - Use JOINs instead
3. Use seek method for pagination - OFFSET is slow for deep pages
4. MATCH AGAINST for text search - 100x faster than LIKE
5. Select only needed columns - Reduces data transfer

Database Security & Access Control

Security Architecture Senior

Problem: Design comprehensive database security measures including access control, encryption, and audit trails.

Security Layers:
  • Network Security: SSL/TLS encryption for data in transit
  • Access Control: Principle of least privilege (grant minimum required access)
  • Data Protection: Encryption at rest and in use
  • Audit & Monitoring: Comprehensive logging and alerting
📋 Complete Security Implementation
-- ============================================ -- DATABASE SECURITY & ACCESS CONTROL -- ============================================ -- 1. USER AND ROLE MANAGEMENT -- Create roles with minimal privileges (Principle of Least Privilege) CREATE ROLE 'app_readonly' IDENTIFIED BY 'secure_password'; CREATE ROLE 'app_readwrite' IDENTIFIED BY 'secure_password'; CREATE ROLE 'app_admin' IDENTIFIED BY 'secure_password'; -- Grant specific privileges to roles GRANT SELECT ON ecommerce.* TO 'app_readonly'; GRANT SELECT, INSERT, UPDATE ON ecommerce.* TO 'app_readwrite'; GRANT ALL PRIVILEGES ON ecommerce.* TO 'app_admin' WITH GRANT OPTION; -- Create users and assign roles CREATE USER 'ecommerce_app'@'%' IDENTIFIED BY 'strong_password_here'; GRANT 'app_readwrite' TO 'ecommerce_app'@'%'; -- 2. ROW LEVEL SECURITY (RLS) - Tenant Isolation -- Implement tenant isolation at database level DELIMITER // CREATE FUNCTION current_tenant_id() RETURNS BIGINT BEGIN RETURN @current_tenant_id; -- Set by application before queries END // DELIMITER ; -- Add tenant_id to all tables ALTER TABLE users ADD COLUMN tenant_id BIGINT NOT NULL DEFAULT 1; ALTER TABLE orders ADD COLUMN tenant_id BIGINT NOT NULL DEFAULT 1; -- Create views with automatic tenant filtering CREATE VIEW user_orders AS SELECT o.* FROM orders o JOIN users u ON o.customer_id = u.id WHERE u.tenant_id = current_tenant_id(); -- Users can only see orders from their tenant -- 3. DATA ENCRYPTION at Rest -- Encrypt sensitive data (SSN, credit cards, etc.) ALTER TABLE users ADD COLUMN encrypted_ssn VARBINARY(255); ALTER TABLE payment_methods ADD COLUMN encrypted_card_number VARBINARY(255); -- Create encryption/decryption functions DELIMITER // CREATE FUNCTION encrypt_data(data TEXT, key_string TEXT) RETURNS VARBINARY(255) BEGIN DECLARE encrypted VARBINARY(255); SET encrypted = AES_ENCRYPT(data, key_string); RETURN encrypted; END // CREATE FUNCTION decrypt_data(encrypted VARBINARY(255), key_string TEXT) RETURNS TEXT BEGIN DECLARE decrypted TEXT; SET decrypted = AES_DECRYPT(encrypted, key_string); RETURN decrypted; END // DELIMITER ; -- Usage Example: -- INSERT INTO users (encrypted_ssn) VALUES (encrypt_data('123-45-6789', 'secret_key')); -- SELECT decrypt_data(encrypted_ssn, 'secret_key') as ssn FROM users WHERE id = 1; -- 4. COMPREHENSIVE AUDIT LOGGING -- Create audit trail table CREATE TABLE audit_log ( id BIGINT PRIMARY KEY AUTO_INCREMENT, table_name VARCHAR(100) NOT NULL, record_id BIGINT NOT NULL, action ENUM('INSERT', 'UPDATE', 'DELETE') NOT NULL, old_values JSON, new_values JSON, user_id BIGINT, ip_address VARCHAR(45), user_agent TEXT, created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, INDEX idx_table_record (table_name, record_id), INDEX idx_timestamp (created_at) ); -- Audit trigger for users table (UPDATE) DELIMITER // CREATE TRIGGER audit_users_update AFTER UPDATE ON users FOR EACH ROW BEGIN INSERT INTO audit_log (table_name, record_id, action, old_values, new_values, user_id) VALUES ('users', NEW.id, 'UPDATE', JSON_OBJECT('email', OLD.email, 'status', OLD.status), JSON_OBJECT('email', NEW.email, 'status', NEW.status), @current_user_id); END // -- Audit trigger for users table (DELETE) CREATE TRIGGER audit_users_delete AFTER DELETE ON users FOR EACH ROW BEGIN INSERT INTO audit_log (table_name, record_id, action, old_values, user_id) VALUES ('users', OLD.id, 'DELETE', JSON_OBJECT('email', OLD.email, 'status', OLD.status), @current_user_id); END // DELIMITER ; -- Query audit log SELECT * FROM audit_log WHERE table_name = 'users' AND record_id = 123 ORDER BY created_at DESC; -- See complete history of changes to user 123
🔒 Security Best Practices:
1. Principle of Least Privilege: Grant minimum required access only
2. Encrypt Sensitive Data: Always encrypt SSN, credit cards, passwords
3. Audit Everything: Log all changes for compliance (HIPAA, GDPR)
4. Row-Level Security: Use views/functions for tenant isolation
5. Regular Reviews: Audit user permissions quarterly

🔗 Joins Quick Summary

Type Meaning Example
INNER JOIN Common in both tables - only matching rows Users with orders (only users who have orders)
LEFT JOIN All from left table + matching from right All users even if they have no orders
RIGHT JOIN All from right table + matching from left All orders even if user doesn't exist
FULL JOIN All from both tables (not directly in MySQL) All users and all orders (use UNION of LEFT and RIGHT)
🧠 Tip: LEFT = keep left, RIGHT = keep right, INNER = only matches

📊 Aggregate Functions

Function Meaning Example
COUNT() Count rows
SELECT COUNT(*) FROM users;
SUM() Add values
SELECT SUM(amount) FROM orders;
AVG() Average value
SELECT AVG(salary) FROM employees;
MAX() Highest value
SELECT MAX(price) FROM products;
MIN() Lowest value
SELECT MIN(age) FROM users;
🧠 Tip: Aggregate = Math on many rows. Always use with GROUP BY for grouped calculations.
